## What the traces show

1. **A diagnoses better and fixes worse.** Of 295 cells: both pass 107, diagnosis passes and the fix fails 58, the fix
   passes and the diagnosis fails 18, neither 112. The 58 sit in three problems: storage_user_unregistered-2 (17), psa
   (18), silent_data_corruption (17).
2. **storage_user_unregistered-2 decides the end-to-end comparison.** Base 3/3, every A variant 0/24. In all three base
   runs the passing fix removed the `args` of the `mongodb-rate` container and deleted and recreated its
   PersistentVolumeClaim. The problem card names recreating the removed database user as the fix. Without this problem
   the end-to-end counts are base 11/30, A 13/30, A +EXCAP 14/30, A +REF 13/27. (Not checked: what the removed `args`
   contained, and why the A runs stop before the same route.)
3. **Two problems are never diagnosed because the agent never looks at the object.** priority_preemption_cascade: 0 of
   26 runs ran any action naming a PriorityClass or preemption; all blame the memory request. gc_capacity_degradation:
   0 of 27 ran an action naming `GOGC`, a LimitRange or resource usage; most say everything is healthy.
4. **FLOW halves the tokens and loses information.** wrong_dns_policy: diagnosis 0/12 with FLOW, 8/12 without it in
   the A family, 3/3 base; 5 of the 12 FLOW runs did run an action naming the DNS policy. The mechanism is not
   verified.
5. **The agent rarely checks a fix before submitting.** Among runs that changed the cluster, 102 of 128 failed fixes
   and 88 of 105 passed fixes were submitted with at most one read step after the last change. This does not separate
   passes from failures; it means a wrong fix is not noticed.
6. **20 mitigation passes had no change to the cluster.** These need the do-nothing calibration before they count.
7. The runs carry four different `git_commit` values. Whether these differ in agent code is not checked.
